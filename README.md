\# MiniPDM — «Состав изделия»



Тестовое задание на разработку упрощённой PDM-системы для хранения конструкторских объектов, их версий и состава изделия.



Приложение поддерживает:



\- импорт CAD-документов из JSON-файлов `.a3d` и `.m3d`;

\- хранение объектов, версий и BOM в PostgreSQL;

\- повторный импорт с учётом состояния текущей версии;

\- состояния версий «В работе», «Утверждено», «Аннулировано»;

\- дерево состава изделия;

\- расчёт массы с учётом вложенности и количества;

\- сводную спецификацию;

\- обнаружение циклических ссылок;

\- поиск по обозначению и наименованию;

\- WPF-интерфейс на MVVM;

\- отчёт по результатам импорта.

\### MiniPdm.Domain



Содержит предметную модель и правила, не зависящие от инфраструктуры:



\- типы объектов;

\- состояния версий;

\- правила переходов между состояниями;

\- валидацию обозначения.



\### MiniPdm.Application



Содержит прикладную логику:



\- абстракции CAD-системы;

\- импорт документов;

\- валидацию импортируемых данных;

\- правила повторного импорта;

\- формирование отчёта;

\- управление состояниями версий;

\- расчёт массы;

\- построение сводной спецификации;

\- модели запросов к хранилищу.



Application не зависит от PostgreSQL, Dapper, JSON или файловой системы.



\### MiniPdm.Infrastructure



Содержит реализацию внешних зависимостей:



\- чтение JSON CAD-документов;

\- поиск файлов в папке;

\- PostgreSQL;

\- Dapper;

\- репозитории;

\- Unit of Work;

\- рекурсивный SQL-запрос дерева состава.



\### MiniPdm.Desktop



WPF-приложение.



Используется MVVM. Бизнес-логика не размещается в code-behind.



Зависимости приложения собираются вручную в одном composition root — `App.xaml.cs` — и передаются через конструкторы.

\# Модель данных



Используются три основные таблицы.



\## `pdm\_object`



Хранит объект PDM:



\- тип объекта;

\- обозначение;

\- наименование;

\- ссылку на текущую версию.



Для `Assembly` и `Part` объект идентифицируется обозначением.



Для `StandardPart` обозначение отсутствует, объект идентифицируется по наименованию.



\---



\## `object\_version`



Хранит версии объектов:



\- номер версии;

\- состояние;

\- материал;

\- массу;

\- дату создания.



Поддерживаются состояния:



```text

InWork     → «В работе»

Approved   → «Утверждено»

Cancelled  → «Аннулировано»

```



Разрешённые переходы:



```text

В работе → Утверждено

В работе → Аннулировано

Утверждено → Аннулировано

```



Обратные переходы запрещены.



Текущей является версия с максимальным номером, не находящаяся в состоянии `Cancelled`.



\---



\## `bom\_link`



Связывает версию родительской сборки с дочерним объектом.



Хранит:



```text

parent\_version\_id

child\_object\_id

quantity

```



Количество должно быть целым числом больше нуля.



Связь хранится именно с дочерним \*\*объектом\*\*, а во время расчётов используется его текущая версия.



\---



\# Работа с CAD



Для доступа к CAD-данным используется абстракция:



```csharp

public interface ICadDocumentReader

{

&#x20;   Task<CadDocument> ReadAsync(

&#x20;       string path,

&#x20;       CancellationToken cancellationToken);

}

```



Application-слой не знает, что данные находятся в JSON-файлах.



Текущая реализация находится в Infrastructure:



```text

JsonCadDocumentReader

```



Таким образом, файловый JSON-reader можно заменить реализацией реального API САПР без изменения бизнес-логики импорта.



Идентификатором CAD-документа является имя файла на диске.

\# Импорт



Обработка папки состоит из нескольких этапов:



```text

Поиск документов

&#x20;       ↓

Чтение через ICadDocumentReader

&#x20;       ↓

Валидация

&#x20;       ↓

Каскадное отклонение зависимых сборок

&#x20;       ↓

Сохранение принятых объектов одной транзакцией

&#x20;       ↓

Формирование отчёта

```



Ошибка чтения одного файла не останавливает импорт остальных документов.



При ошибке сохранения транзакция откатывается.

\# Повторный импорт и версии



При повторном импорте уже существующего объекта:



\### Данные не изменились



Ничего не изменяется.



Результат:



```text

Unchanged

```



\### Текущая версия «В работе»



Изменяется существующая версия.



Новая версия не создаётся.



\### Текущая версия «Утверждено»



Создаётся следующая версия:



```text

N + 1

```



в состоянии:



```text

В работе

```



Утверждённая версия остаётся неизменной.



\### Все предыдущие версии аннулированы



Создаётся версия со следующим номером, а не снова версия №1.



\---



\# Дерево состава



Полное дерево BOM загружается из PostgreSQL одним запросом с рекурсивным CTE.



Для каждого узла определяются:



\- объект;

\- текущая версия;

\- непосредственное количество;

\- суммарное количество по пути;

\- глубина;

\- признак цикла.



Таким образом, дерево не строится серией SQL-запросов из C#.



\---



\# Расчёт массы



Масса сборки рассчитывается по всем листовым компонентам дерева.



Для вложенных сборок количества перемножаются по пути.



Пример:



```text

Сборка

└── Узел ×2

&#x20;   └── Деталь ×3

```



Количество детали для расчёта:



```text

2 × 3 = 6

```



Если у любого необходимого компонента отсутствует масса, приложение \*\*не возвращает неполную сумму и не подставляет ноль\*\*.



Вместо этого:



\- расчётная масса считается недоступной;

\- пользователю показывается компонент, у которого отсутствует масса;

\- компонент остаётся в сводной спецификации с пустым значением массы.



\---



\# Сводная спецификация



Сводная спецификация содержит плоский список всех деталей и стандартных изделий.



Если одинаковый объект встречается в нескольких ветках дерева, его количества:



1\. умножаются по каждому пути;

2\. складываются между путями.



Сборки в итоговую плоскую спецификацию не включаются.



\---



\# Циклические ссылки



Цикл в BOM обнаруживается при чтении структуры.



Например:



```text

A

└── B

&#x20;   └── C

&#x20;       └── A

```



Рекурсия останавливается, а расчёт возвращает диагностическую ошибку вместо бесконечного обхода.



В тестовом наборе также присутствует реальный циклический состав, который отображается в интерфейсе с пометкой `\[ЦИКЛ]`.



\---



\# Валидация импортируемых данных



Проверяются, в частности:



\- корректность формата обозначения;

\- уникальность обозначений Assembly/Part;

\- уникальность наименований StandardPart;

\- обязательность материала для Part;

\- отсутствие материала у Assembly и StandardPart;

\- масса;

\- отсутствие BOM у Part и StandardPart;

\- количество компонента больше нуля;

\- существование всех файлов, на которые ссылается сборка;

\- каскадное отклонение сборки при отклонении её компонента;

\- дубликаты компонентов в одном BOM.



Формат обозначения:



```text

АБВГ.301245.001

```



То есть:



```text

4 заглавные кириллические буквы

.

6 ASCII-цифр

.

3 ASCII-цифры

```

\## Обнаруженные ошибки



| Файл | Результат | Причина |

|---|---|---|

| `Отдушина.m3d` | Ошибка | Некорректный JSON |

| `Втулка распорная.m3d` | Ошибка | Некорректное обозначение: используется латинская `P` |

| `Кольцо распорное.m3d` | Ошибка | Некорректный формат обозначения |

| `Шайба стопорная.m3d` | Ошибка | Дублирующееся обозначение |

| `Шайба упорная.m3d` | Ошибка | Дублирующееся обозначение |

| `Привод масляного насоса.a3d` | Ошибка | Ссылка на отсутствующий файл `Насос шестерённый НШ-10.m3d` |

| `Пробка сливная в сборе.a3d` | Ошибка | Количество компонента равно 0 |

| Файл | Результат | Причина |

|---|---|---|

| `Прокладка маслоуказателя.m3d` | Предупреждение | Не указана масса |

\# Проверка `cad-export-v2`



`cad-export-v2` представляет ту же модель после изменений конструктора.



По сравнению с первой версией изменены два CAD-документа.



\## `Колесо зубчатое.m3d`



Было:



```text

```



Стало:



```text

mass = 5.92 кг

```

Количество компонента:



```text

Прокладка регулировочная.m3d

```



изменено:



```text

3 → 4

```

\## Проверка версионности



Перед импортом `cad-export-v2` обе изменённые версии объектов были переведены в состояние:



```text

Утверждено

```



После импорта `cad-export-v2` получен результат:



```text

Принято: 38

Отклонено: 7

Предупреждений: 1



Создано: 0

Обновлено: 0

Новых версий: 2

Без изменений: 36

```



Для обоих изменённых объектов созданы версии №2 в состоянии \*\*«В работе»\*\*.



\### Колесо зубчатое



История:



```text

Версия 1 — Утверждено — масса 5.86 кг

Версия 2 — В работе     — масса 5.92 кг

```



Текущей является версия №2.



\### Крышка подшипника в сборе



История:



```text

Версия 1 — Утверждено

Версия 2 — В работе

```



В BOM версии №2:



```text

Прокладка регулировочная × 4

```



Расчётная масса после изменения:



```text

1.2284 кг

```



Таким образом, утверждённая версия №1 остаётся неизменной, а изменённые данные импортируются в новую рабочую версию.

\# Принятые архитектурные решения



\## `current\_version\_id`



Поле хранится в `pdm\_object`, несмотря на некоторую избыточность.



Это позволяет:



\- быстро получить текущую версию;

\- упростить рекурсивный запрос BOM;

\- избежать поиска текущей версии для каждого дочернего объекта во время рекурсии.



Ссылка обновляется при создании и аннулировании версий.



\---



\## Масса сборки не хранится



Масса `Assembly` не записывается в `object\_version`.



Она всегда рассчитывается по актуальному дереву состава.



Это исключает рассинхронизацию сохранённой массы и BOM.



\---



\## Цикл не является ошибкой импорта



Все ссылки в цикле могут быть корректными с точки зрения существования объектов.



Поэтому структура импортируется, а цикл обнаруживается на этапе обхода BOM и расчётов.



Так можно сохранить исходные данные и одновременно гарантировать отсутствие бесконечной рекурсии.



\---



\## Деталь без массы импортируется



Отсутствие массы у `Part` считается предупреждением, а не ошибкой.



При последующем расчёте массы сборки система явно сообщает, у какого компонента масса отсутствует.



\---



\## Отчёт и внутренние сообщения разделены



Application-слой использует технические статусы и диагностические сообщения.



Преобразование в пользовательские русскоязычные сообщения выполняется в Desktop-слое.



Это не связывает бизнес-логику с конкретной локализацией интерфейса.

\# Что не реализовано



Необязательная часть задания реализована не полностью.



Не реализованы:



\- ленивая загрузка дочерних узлов дерева;

\- отображение процента выполнения импорта;

\- отмена уже запущенного импорта из интерфейса;

\- поддержка MS SQL;

\- экспорт спецификации в CSV/XLSX;

\- отдельный экран сравнения двух версий;

\- структурированное логирование через Serilog.



Эти возможности не влияют на обязательную функциональность.



При дальнейшем развитии:



\- lazy loading можно реализовать отдельным запросом непосредственных дочерних узлов;

\- прогресс и отмену импорта — через `IProgress<T>` и `CancellationToken`;

\- второй SQL provider — реализациями существующих persistence-абстракций;

\- экспорт спецификации — поверх готового результата `BomCalculationService`;

\- сравнение версий — сравнением двух сохранённых BOM по `child\_object\_id` и `quantity`;

\- структурированное логирование — через DI и `Microsoft.Extensions.Logging`/Serilog.
